# DressCodeJS

DressCodeJS — методология построения архитектуры JavaScript-приложений и утилита сборки JS-кода, написанного по этой методологии (построена на Jossy).

## Четыре главных правила

1. **Компонент именован в CamelCase** — имя начинается с заглавной буквы. Сборщик по имени определяет, что есть компонент.
2. **Каждый компонент лежит в своём файле** с именем, совпадающим с именем компонента: `MyProject/App.js` описывает компонент `MyProject.App`.
3. **Корневой объект** (объект, содержащий вложенные классы/функции) = папка с именем, совпадающим с именем объекта, плюс файл `index.js`, в котором объект объявляется: папка `MyProject/Forms/` с `MyProject.Forms = {}` в `index.js` — это компонент `MyProject.Forms`.
4. **Зависимости не объявляются**: сборщик смотрит, какие имена используются в коде, и сам подключает нужные файлы.

## Компоненты: что видит сборщик

| Расположение | Компонент |
|---|---|
| `index.js` в папке | корневой объект с именем папки: `MyProject/index.js` → `MyProject` |
| файл `Имя.js` в подпапке | член корневого объекта: `MyProject/App.js` → `MyProject.App` |
| подпапка (с `index.js`) | вложенный объект: `MyProject/Forms/index.js` → `MyProject.Forms` |

Правила имён и видимости:

- Имя компонента: **только буквы и цифры, первая — заглавная** (ни `_`, ни `-` не допускаются).
- Файлы **в корне библиотеки** (кроме `index.js`) и файлы **со строчными именами** сборщик не видит — положите их в папку-компонент.
- При подключении компонента вместе с ним **всегда** подключается объявление его корневого объекта (содержимое соответствующего `index.js`), даже если код его напрямую не использует.

Пример структуры:

```
+ MyProject
|-- + Forms
|    |-- index.js      # MyProject.Forms = {};
|    |-- Abstract.js   # MyProject.Forms.Abstract = Bricks.inherit();
|-- index.js           # var MyProject = {};
`-- App.js            # MyProject.App = Bricks.inherit({...});
```

## Структура проекта

Типовой проект:

```
project/
|-- .dresscode
|-- static/
|   |-- js-dev/        # приложение: скрипты, подключаемые на страницы
|   `-- js-libs/       # библиотека
|       `-- MyProject/
`-- node_modules/
```

- **Библиотека** (`js-libs`) — каталоги, объявленные в `.dresscode`. В библиотеках нет запускаемого кода, только описания классов и функций: собранная библиотека, подключённая на страницу, ничего не делает.
- **Приложение** (`js-dev`) — скрипты, подключаемые на страницы сайта: создание объектов, настройка, привязка к странице.

### Файл .dresscode

Объявляет, какие каталоги являются библиотеками. Текстовый файл: **одна строка — один путь** (относительный или абсолютный) до каталога-библиотеки:

```
static/js-libs
node_modules/<имя пакета>/lib
```

- Для собираемого файла утилита ищет `.dresscode` вверх по дереву: в директории файла, затем выше, до корня. Обычно файл один на весь проект и лежит в его корне.
- Пакет, выпущенный отдельно, несёт собственный `.dresscode` в корне библиотеки.
- Внешние библиотеки подключаются **по пути**, а не по версии: в билд попадает ровно тот код, что сейчас лежит по указанному пути. Воспроизводимость дают зафиксированные версии в `package.json`/`package-lock.json`.
- Путь, по которому каталог **не найден**, молча пропускается: одна и та же библиотека может быть объявлена двумя путями (напр. `node_modules/dresscode-quantum/lib` при разработке рядом и `../../../node_modules/dresscode-quantum/lib` при npm-hoisting в потребителе) — в каждом layout существует ровно один.
- Если **оба** пути существуют — ошибка сборки: одно имя компонента достижимо из двух мест. Оставьте один путь.

## Как код попадает в сборку

Если в коде есть обращение к имени, сборщик подключает соответствующий файл вместе со всем, что использует он, и так далее:

| Как написано | Что это | Что попадёт в сборку |
|---|---|---|
| `Foo.bar` — со строчной буквы | свойство компонента | компонент `Foo`; из его файла — только используемые свойства |
| `Foo.Bar` — в CamelCase | вложенный компонент | файл компонента `Foo.Bar` |
| `Foo.VERSION` — целиком в капсе | «константа» компонента | компонент `Foo` |

Два момента:

- **В сборку попадает только нужное**: из `index.js` корневого объекта, содержащего много свойств, попадут лишь реально используемые свойства.
- **Подключаемые файлы выводятся в начале** выходного файла, перед его собственным кодом. Если файл завернут в скоуп и подключения должны попасть внутрь него — переместите блок подключений `//#imports` в нужное место.

Все библиотеки, используемые в коде, **должны быть объявлены в `.dresscode`** — иначе сборщик не увидит их компоненты.

## Макрос $$

В **компонентном** файле (файле, описывающем компонент) сборщик заменяет все вхождения `$$` на имя компонента. Допускается суффикс: `$$`, `$$__suffix` (буквы, цифры, `_`, `-`). Это даёт имена методов и CSS-классов, не пересекающиеся с именами из других файлов. Подстановка — по всему файлу, в том числе внутри строк-литералов.

- **Debug-сборка** (`-d`): `$$` → имя компонента с точками, заменёнными подчёркиваниями: `MyProject_Forms_Abstract`.
- **Production-сборка**: `$$` → короткое приватное имя `_0_`, `_1_`, …; одно и то же имя получает одно и то же приватное имя в пределах сборки.
- **Стабильность между сборками — только через `--private-dict`**: словарь читается перед сборкой и записывается после. Если код собирается в **несколько** выходных файлов (страницы, бандлы), один и тот же файл словаря **обязательно** передавать во все сборки — иначе одинаковый `$$`-член в разных файлах получит разные имена.
- Сборки, работающие с **одним и тем же** словарём, **нельзя запускать параллельно** (последний писавший перезаписывает имена остальных) — только последовательно.

В **не-компонентном** файле (скрипт `js-dev`, файл в корне библиотеки) `$$` остаётся литеральным текстом — это осознанная семантика.

## Директивы

Директива пишется на отдельной строке (`//#имя аргумент`) или инлайном в строке (`/*#имя аргумент#*/`).

| Директива | Назначение |
|---|---|
| `//#require Component` | явно подключить компонент — вместе со всем, что он использует |
| `//#require Component.member` | подключить компонент, но из его файла — только свойство `member` |
| `//#require Component['member']` | то же; в скобках — только строковый литерал |
| `//#imports` | вывести блок подключённых файлов в этой точке файла (по умолчанию — в начале) |
| `//#without file.js` | исключить из сборки файл вместе с тем, что подключает он |
| `//#if flag` / `//#endif` | выводить код в зависимости от флага (`//#if not flag` — при его отсутствии) |
| `//#set flag` / `//#unset flag` | задать / снять флаг |
| `//#layer name` / `//#endlayer` | слой кода (см. ниже) |

`#require` в большинстве случаев не нужен — DressCode сам подключает зависимости. Нужен он, когда в базовый файл сайта должен попасть код, не используемый в этом файле, но используемый во всех остальных: напр. компоненты `MyProject.App1`/`MyProject.App2` наследуют `MyProject.AbstractApp`, сборка идёт в `index.js` + `app1.js` + `app2.js` — тогда в `index.js` пишем `//#require MyProject.AbstractApp`, а в `app1.js`/`app2.js` — `//#without index.js`.

DressCode поддерживает и остальные директивы Jossy.

## Условная сборка и слои

Флаги `--set` и `//#set`/`//#if` позволяют компилировать разные версии кода:

```js
//#if lang_ru
alert('Русский интерфейс');
//#endif

//#if debug
console.log(...);
//#endif
```

`-d, --debug` автоматически задаёт флаг `debug` — отладочные строки не попадают в боевые сборки.

Слои позволяют собрать **только** код слоя, исключив базовый:

```js
//#layer test
MyProject.App = FakeApp;
//#endlayer
realInit();
```

- без параметров — только базовый код (`realInit()`);
- `--layer test` — только код слоя;
- `--layers test` — базовый код плюс слой (`--layer` и `--layers` несовместимы).

## Сборка

### Командная строка

```
./node_modules/.bin/dresscodejs -i static/js-dev/index.js -o static/js/index.js
```

| Параметр | Назначение |
|---|---|
| `-i, --input <path>` | (обязательно) файл для сборки, или папка (см. Сборка папки) |
| `-o, --output <path>` | файл результата; если не указан — `stdout` (только файл-режим); в папочном режиме — папка и обязателен |
| `-d, --debug` | не переименовывать приватные имена + флаг `debug` |
| `--set <flag>` | (можно многократно) булевы флаги для `//#if` |
| `--layer <name>` | собрать **только** код слоя `//#layer name`; несовместимо с `--layers` |
| `--layers <name>` | (можно многократно) базовый код плюс перечисленные слои |
| `--private-dict <path.json>` | словарь приватных имён `$$`: читается перед сборкой, записывается после |
| `--fail-on-errors` | при ошибке сборки завершить с кодом 1 |

Боевая сборка с условной компиляцией и стабильным словарём:

```
./node_modules/.bin/dresscodejs -i static/js-dev/index.js -o static/js/index.js --set ie --private-dict private-names.json
```

Про ошибки: по умолчанию ошибка сборки (неизвестная директива, компонент из `#require` не найден и т.п.) вкладывается в результат как `throw new Error("DresscodeError: …")` — файл соберётся, но упадёт с диагностикой при выполнении. Для CI — `--fail-on-errors`. Ошибка дубликата имени компонента (`.dresscode`) завершает сборку с кодом 1 **в любом режиме**.

### Сборка папки

`-i <папка>` — все js-файлы в ней (рекурсивно, в отсортированном порядке — индексы приватных имён стабильны); каждый файл получает собственный результат в `-o` с сохранением структуры (`js-dev/app/page.js` → `js/app/page.js`).

```
./node_modules/.bin/dresscodejs -i static/js-dev -o static/js --private-dict private-names.json
```

Нюансы:

- `-o` (папка) **обязателен**; `-o === -i` — ошибка (in-place пересборка исходников).
- Вся папка собирается **одним экземпляром DressCode** — общий словарь `$$` во всех выходных файлах.
- Сам выходной каталог в сбор не попадает, если лежит внутри входного (`-i . -o build`).
- Пропусков нет: собираются все `*.js`, включая `node_modules` и dot-каталоги.
- Ошибки: как в файл-режиме; с `--fail-on-errors` — прерывается на первой, словарь не пишется.

### Использование из Node.js

```js
var {DressCode} = require('dresscodejs');

var dresscode = new DressCode(
    false, // debug: не переименовывать приватные имена
    false  // failOnErrors: выбрасывать исключение при ошибке сборки
);

dresscode.compile('static/js-dev/index.js', {debug: true}).then((result) => {
    fs.writeFileSync('static/js/index.js', result);
});
```

- `compile(file, context, labels, layers)` — `context`: объект булевых флагов для `//#if`; `labels`: области собираемого файла (`['']` — только базовый код, список имён — базовый код плюс перечисленные области); `layers`: строка (только слой) или массив (база плюс слои).
- `compileCode(virtualFile, content)` — собирает строку кода как файл по указанному пути.
- Прочитанные файлы кэшируются в экземпляре: один экземпляр удобно использовать для нескольких связанных файлов. Если исходники изменились — `dresscode.clearCache()` (кэш не перепроверяется по диску) либо новый экземпляр.
- `setPrivateNamesDict(names)` / `getPrivateNamesDict()` — то, что CLI делает через `--private-dict`.

## Установка проекта

1. `npm install --save-dev dresscodejs`
2. Создать `static/js-dev` (скрипты страниц) и `static/js-libs` (библиотека).
3. В корне проекта — файл `.dresscode` со строкой `static/js-libs`.
4. Внешние библиотеки: npm devDependency + путь до её каталога-библиотеки в `.dresscode` (напр. `node_modules/<пакет>/lib`).
5. Настроить [Yaxy](https://github.com/Kolyaj/Yaxy) для сборки на лету.

### Разработка через Yaxy

Правая часть правила Yaxy поддерживает протокол `bin:` — команда, `stdout` которой возвращается как ресурс:

```
# .yaxy
site.my/static/js/index.js => bin: dresscodejs -i ~/static/js-dev/index.js
site.my => localhost:3000
```

`yaxy --config .yaxy` — каждый запрос к `site.my/static/js/index.js` в браузере получает свежесобранный файл.

## Существующие библиотеки

- [Bricks](https://github.com/Kolyaj/Bricks) — базовые классы и функции (`Bricks.inherit`).
- [dresscode-quantum](https://github.com/Kolyaj/dresscode-quantum) — `Quantum`: объекты с изменяющимся значением и синхронно обновляющиеся цепочки (синхронизация UI с состоянием).
- [dresscode-botex](https://github.com/Kolyaj/dresscode-botex) — `Botex`: шаблонизатор и библиотека построения UI.
- [dresscode-binary](https://github.com/Kolyaj/dresscode-binary) — `Binary`: кодирование данных в компактный бинарный формат.
- [dresscode-resources](https://github.com/Kolyaj/dresscode-resources) — компилятор бинарных файлов в JS-код (ресурсы в сборку).
- [dresscode-polyfills](https://github.com/Kolyaj/dresscode-polyfills) — полифиллы для старых браузеров.

## Ограничения

- Код разбирается как **ES2022** (`esprima-next`): `?.`, `??`, class fields, BigInt — поддерживаются; более новый синтаксис — нет.
- Файл с синтаксической ошибкой проходит **необработанным**: исходный текст попадает в результат, ошибку вы увидите при выполнении. В debug-режиме и с `--fail-on-errors` выводится предупреждение, сборка не прерывается.

## Частые ошибки

| Симптом | Причина / решение |
|---|---|
| Компонент не попадает в сборку, имя «не видно» | библиотека не объявлена в `.dresscode` (ищите файл вверх по дереву) |
| Имя файла/папки со строчной буквы или с `_`/`-` | сборщик не видит: переименовать в CamelCase (буквы и цифры) |
| Файл лежит в корне библиотеки | компонентом становится только `index.js`; остальные — в папку |
| Ошибка «duplicate cname» | одна библиотека объявлена в `.dresscode` двумя путями, и оба существуют — оставить один |
| Приватные имена `$$` «плывут» между сборками | несколько выходных файлов без общего `--private-dict`, или параллельные сборки на один словарь |
| `$$` не подставлен | файл не компонентный (js-dev-скрипт, файл в корне библиотеки) — так задумано |
| Код нужен в базовом файле, но там не используется | `//#require Component` + `//#without index.js` в остальных |
| Подключения должны попасть внутрь скоупа | `//#imports` в нужное место |
